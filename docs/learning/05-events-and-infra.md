# 5. События и инфраструктура

## Синхронно (gRPC) или через события (NATS)

| | gRPC-вызов | Событие в NATS |
|---|---|---|
| Аналогия | `await fetch()` — ждём ответ | `emitter.emit('created')` — сообщили и пошли дальше |
| Когда | нужен ответ прямо сейчас (проверить токен, получить заявку) | «что-то произошло», а кто и как отреагирует — не наше дело |
| Если получатель упал | ошибка у вызывающего | сообщение подождёт в очереди и будет доставлено позже |

## NATS JetStream

**NATS** — брокер сообщений: сервисы публикуют сообщения в «темы» (subjects), другие сервисы на них подписываются. **JetStream** — режим, в котором сообщения сохраняются на диск, поэтому не теряются, пока подписчик выключен.

- **Stream `CARGO`** — хранилище всех событий с темами `shipment.*` и `tracking.*`.
- **Subjects** (темы): `shipment.created`, `shipment.status_changed`, `tracking.position_updated`.
- **Durable consumer** — именованная подписка (`tracking`, `notification`). NATS помнит, до какого сообщения она дочитала. Выключил notification на час — после включения он получит всё пропущенное.
- **Ack** — подписчик подтверждает «обработал». Нет подтверждения или ошибка — NATS пришлёт сообщение ещё раз (до 5 попыток).

Формат событий описан в [proto/events/v1/events.proto](../../proto/events/v1/events.proto), на проводе — бинарный protobuf. Посмотреть стрим можно в мониторинге NATS: http://localhost:8222/jsz?streams=true.

### Идемпотентность

Раз сообщение может прийти дважды, обработчик должен быть **идемпотентным**: повторная обработка ничего не ломает. tracking использует ID события как ID строки и пишет `INSERT ... ON CONFLICT DO NOTHING` — второй раз вставка просто не произойдёт.

### Outbox: зачем такая сложность

Наивный вариант в shipment:

```
1. INSERT в Postgres
2. publish в NATS
```

Если сервис упадёт между шагами 1 и 2 — заявка есть, а события нет, tracking и notification о ней не узнают. Если поменять шаги местами — событие ушло, а заявка не сохранилась.

**Transactional outbox:** событие пишется в таблицу `outbox` **в той же транзакции**, что и заявка. Либо сохранятся оба, либо ничего. Отдельный цикл (relay) раз в секунду дочитывает `outbox` и отправляет в NATS. Сервис упал — после перезапуска relay доотправит.

## Базы данных

**Postgres** — у каждого сервиса своя база: `auth`, `shipment`, `tracking`. Сервис никогда не лезет в чужую — только через gRPC или события. Так сервисы можно менять и деплоить независимо.

**Redis** — быстрое хранилище «ключ → значение» в памяти, общее для всех, у каждого сервиса свой префикс ключей:

| Ключ | Кто | Зачем |
|---|---|---|
| `refresh:<id>` | auth | активные refresh-токены (с TTL 7 дней) |
| `shipment:<id>` | shipment | кеш заявок, 5 минут |
| `rl:<ip>:<окно>` | gateway | счётчики rate limit |

### Миграции (goose)

Схема базы описана SQL-файлами в `services/<имя>/migrations/` — как миграции Prisma или Knex. Каждый файл — шаг с номером, внутри `-- +goose Up` (применить) и `-- +goose Down` (откатить).

- `make migrate-up` — применить все новые;
- `make migrate-status` — что уже применено;
- в Docker и на Render сервис применяет их сам при старте (`MIGRATE_ON_START=true`).

### Запросы (sqlc)

ORM нет. SQL пишется руками в `services/<имя>/queries/*.sql`, а **sqlc** генерирует из него типизированные Go-функции:

```sql
-- name: GetShipment :one
SELECT * FROM shipments WHERE id = $1;
```

→ `make sqlc` →

```go
func (q *Queries) GetShipment(ctx context.Context, id uuid.UUID) (Shipment, error)
```

Похоже на Prisma Client, только источник — твой SQL, а не схема Prisma. Ошибся в имени колонки — `make sqlc` упадёт ещё до запуска.

## Docker и docker-compose

- **Dockerfile** у каждого сервиса: собрать Go-бинарник и положить его в минимальный образ (~40 МБ, внутри даже нет shell).
- **[docker-compose.yml](../../deploy/docker-compose.yml)** — инфраструктура для локальной разработки:

| Контейнер | Порт на твоём компьютере | Зачем |
|---|---|---|
| postgres | 5434 | базы auth, shipment, tracking |
| redis | 6379 | кеш, сессии, rate limit |
| nats | 4222, мониторинг 8222 | события |
| jaeger | UI 16686, приём трейсов 4317 | трейсы |

Профиль `apps` дополнительно поднимает все 5 Go-сервисов (`make apps-up`).

## Makefile — это `npm run`

`make <цель>` — как `npm run <script>`. `make help` выведет весь список. Главное:

| Команда | Что делает |
|---|---|
| `make infra-up` / `infra-down` | поднять / остановить инфраструктуру |
| `make migrate-up` | применить миграции |
| `make apps-up` / `apps-logs` | все сервисы в Docker / их логи |
| `make run-all` | всё сразу: инфраструктура, миграции и 5 сервисов в одном терминале |
| `make proto` | перегенерировать код из `.proto` |
| `make sqlc` | перегенерировать код из SQL |
| `make test` / `make lint` | тесты / линтер |

## Конфигурация: .env

Все настройки — переменные окружения (как `process.env`). Локально сервисы сами читают `.env` из корня. В Docker и на Render `.env` нет — переменные задаются снаружи (`docker-compose.yml`, панель Render). Описание каждой — в [.env.example](../../.env.example).

## Здоровье сервисов

У каждого сервиса два служебных эндпоинта:

- `/healthz` — «процесс жив», всегда 200;
- `/readyz` — «готов работать»: проверяет базу, Redis, NATS. Например, `curl localhost:8080/readyz` → `{"auth":"ok","redis":"ok",...}`. Если что-то упало — 503 и видно, что именно.

Порты: gateway 8080, auth 8081, shipment 8082, tracking 8083, notification 8085 (у notification ещё gRPC 50054).

## Трейсинг (OpenTelemetry + Jaeger)

**OpenTelemetry** — стандарт записи трейсов. Каждый сервис отправляет «спаны» (кусочки работы с временем начала и конца) в **Jaeger**. Связывает их **trace ID**, который передаётся дальше в заголовке `traceparent`: в HTTP, в gRPC metadata, в заголовках NATS-сообщений и даже через таблицу outbox. Поэтому в Jaeger видна вся цепочка, включая асинхронную часть.
